Frugal solar forecasting: how much model a deployed forecast needs

Principle 3 · Complexity only if it paysThe approach

In the story: climb only if it pays, how much model a forecast really needs before it is deployed.

In brief

  • Deploying a forecast on a small device makes the model's size part of the problem: memory, latency and energy count as well as the error.
  • Models of increasing capacity are compared with persistence on the same data, and extra capacity is kept only when its gain is worth its cost.
  • C. Voyant, M. Leiva, X. Silvani, G. Notton, L. Garcia-Gutierrez, A. Julien, G. Chesnoiu, K. Abdeladim and T. Carriere, manuscript in preparation; benchmark code PV_ELM_pred, doi:10.5281/zenodo.21487267.

Solar forecasting: why deploy frugal models?

The best model is not determined by forecast error alone. It must also fit the available device, respond on time and remain maintainable.

Why consider deployment from the start?

A forecast may run at a weather station, battery controller or near an inverter. These devices do not all have a GPU, ample memory or continuous cloud connectivity. The computing budget is part of the forecasting problem.

Local inference can reduce network dependence and data transfers. It still requires device security, error monitoring and model updates when operating conditions change.

Frugal does not mean simplistic

The principle is to justify additional complexity. A clearly defined persistence forecast, followed by linear autoregression, provides an informative starting point. A richer model is useful when its gains are robust and valuable relative to its cost.

An ELM uses randomly fixed hidden-layer weights and fits the output weights. It offers a way to study nonlinear forecasting with a simple fitting procedure. This does not guarantee the best forecasts everywhere or negligible memory use: fixed weights must also be stored.

What do we gain by adding capacity?

If two models both meet a control application’s requirements, a much larger memory footprint deserves justification. Conversely, a modest error improvement may be valuable if it avoids a costly decision. Model selection depends on use, not size alone.

The PV_ELM_pred repository compares persistence, BLEND, linear autoregression and ELM variants under a common protocol. A capacity sweep helps examine accuracy alongside stored parameter count.

The theory

Two quantities decide whether more model is worth it: the error gain against a fixed reference, and the cost of the model on the device.

Extreme learning machine (ELM)

For an input row \(\mathbf x\in\mathbb R^{d}\), a hidden layer of \(L\) neurons with weights \(W\in\mathbb R^{L\times d}\) and biases \(\mathbf b\in\mathbb R^{L}\) drawn at random and never trained:

$$\mathbf h(\mathbf x)=g\!\left(W\mathbf x+\mathbf b\right),$$ $$\hat{\mathbf y}=\mathbf h(\mathbf x)^{\top}\beta .$$

Only the output weights \(\beta\) are fitted, in closed form, on the \(N\) training rows stacked in \(H\in\mathbb R^{N\times L}\) and the targets \(Y\):

$$\beta=\left(H^{\top}H+\lambda I\right)^{-1}H^{\top}Y\quad(\text{ridge}),$$ $$\beta=H^{+}Y\quad(\lambda\to0,\ \text{Moore–Penrose pseudo-inverse}).$$

Training is one linear solve, so it takes seconds; several outputs share the same \(H\). Stored parameters for one output: \(dL+L+(L+1)\) (input weights, biases, output weights with intercept). ELM: Huang, Zhu and Siew (2006).

Score against simple persistence

Errors are compared on the same samples with \(\mathrm{NICE}^{k}=L^k\text{-Error}_X/L^k\text{-Error}_P\), where \(L^k\text{-Error}=\big(\tfrac1n\sum|y-\hat y|^{k}\big)^{1/k}\) and P is simple persistence: 0 for a perfect forecast, 1 for persistence (NICE guide).

Memory of the parameters alone

$$M=4\,P\ \text{bytes (float32)},$$ $$P=dL+L+(L+1)\ \text{for an ELM with one output}.$$

Inputs, temporary arrays and software add to \(M\); latency and energy are not functions of \(P\) and must be measured on the target device.

Worked example: more model, for what gain?

Model A stores 100 parameters and has an RMSE of 100 W. Model B stores 10,000 parameters and achieves 95 W on the same observations and horizon: 100 times as many parameters for 5% lower RMSE. That may be worthwhile, but the error score alone does not settle deployment.

With float32 storage, the parameters alone occupy about 400 bytes for A and 40,000 bytes for B. Inputs, temporary arrays and software add overhead. Latency and energy cannot be inferred from these counts; measure them on the target device.

If persistence has an RMSE of 125 W, the two error ratios are 0.80 and 0.76. Both beat that reference in this example, at very different storage costs. This is a fictitious teaching example, not a ranking from the ongoing studies.

What should be measured on the device?

  • Forecast quality: identical dates and horizons, an explicit baseline and stability across periods.
  • Deployment: actual memory use, response time, update cost and offline behavior.
  • Energy: measurements on the target hardware, distinguishing preprocessing, fitting and operation.
Fewer parameters do not prove lower energy use or carbon emissions. A model-size benchmark is not a complete embedded-system validation.

Where does the approach stop?

Forecasting a channel from its own history explores local short-term prediction. It does not automatically replace numerical weather prediction for day-ahead forecasting or physical models when these add useful information. Wind, load and other renewable-energy applications require their own validation.

Reducing input dimensionality and reducing model capacity are separate levers. Combining them requires evaluating the entire pipeline and the final forecast.

Open code and research in progress

The associated first-author manuscript, How Much Model Is Enough for Endogenous, Edge-Oriented Solar and Weather Forecasting?, is in preparation. This page does not publish its numerical findings or rankings.

The public Python repository is the current entry point for the models, protocol and data-access conditions. The Palaiseau example is supplied; other datasets can have separate access requirements.
